# IMPLEMENTATION RESULT

## Work Item

CD-01 — Tenant registry moves from code to the database.

The client → template *assignment* moved off `CLIENT_SLUG_TEMPLATE_MAP` in
`lib/templates/index.ts` onto a new `clients.template_key` column;
`TEMPLATE_REGISTRY` (the catalogue of templates that *exist*) stayed in code;
`clients.isActive` is now enforced in `getTenantBySlug()`; the two falsified
comments (`lib/templates/index.ts`, `lib/domains.ts`) were rewritten.

Implemented against `work/CD-01-tenant-registry/architecture-plan.md`
(`## Manager Approval` → APPROVED), working its 11-step `## Implementation
Sequence` in order.

## Outcome

Complete. All 9 acceptance criteria PASS with observed evidence. No user-visible
change: every page of every tenant returns the same status code and renders the
same template as before, and the per-tenant prerendered-route counts are
identical for all six tenants.

Two deliberate behaviour changes shipped, both required by the task:
`is_active = false` now 404s, and a `realestate` row whose `template_key` is
null **or unrecognised** now 404s fail-closed.

## Implemented Components

1. **`clients.template_key`** — nullable `varchar(60)`, backfilled for the five
   real-estate rows in the same migration.
2. **`templateKeyFor(tenant)`** — the new accessor in `lib/templates/index.ts`.
   Synchronous, takes the row, validates the stored value against
   `TEMPLATE_REGISTRY`, returns `TemplateKey | undefined` — the identical return
   type `getTemplateKeyForSlug` had, which is what makes all 37 substitutions
   provably type-equivalent. Fail-closed: an unrecognised value returns
   `undefined` exactly as a null does.
3. **`getTenantPath(tenant)`** — signature changed from `(vertical, clientSlug)`
   to the row. Declared with a **structural** parameter type, not
   `import type { Tenant }`, so `lib/templates/index.ts` still has no path to
   `lib/db/schema` (AC 8).
4. **`getTenantBySlug()`** — gains the `isActive` guard, checked **first**, and
   its template guard re-sourced from the row.
5. **`StaticParamTenant`** — `activeTenants()`'s projection widened to carry
   `vertical` and `templateKey`. This is the increment's silent-failure
   prevention; see *Rendering and Caching*.
6. **Seed path** — `profile.yaml` gains `template:`, `scripts/seed-client.ts`
   writes it to `clients.template_key`.

Deleted: `CLIENT_SLUG_TEMPLATE_MAP`, `getTemplateKeyForSlug`,
`getTemplateUrlSlugForClientSlug`.
Kept untouched: `TEMPLATE_REGISTRY`, `URL_SLUG_TO_KEY`, `getTemplateConfig`,
`isTemplateUrlSlug`, `getTemplateKeyForUrlSlug`.

## Rendering and Caching

**Unchanged for every route, and that was the acceptance bar.**

- Public pages still take the tenant from `params` via
  `getTenantBySlug(params.tenant)`. **No page gained a `headers()` call.**
  `templateKeyFor()` is a pure function over a value the page already holds.
- `generateStaticParams` return shapes unchanged — `paramsForEachTenant` still
  spreads `{ tenant: tenant.slug, ...row }`, so every nested dynamic route still
  returns the **complete** param set including the ancestor `tenant`. Only the
  *type* of the object handed to the callback widened.
- `export const revalidate = 300` on `builders/[slug]` and `sectors/[sector]`
  stays; the "no `force-static`" comments in both files are untouched.
- The accessor stays **synchronous**, so `basePathFor()` and `getTenantPath()`
  stay synchronous and the whole internal-link layer — including the
  `components/realestate/premium-v2/*` components that call `basePathFor(tenant)` —
  is untouched.

**The trap the brief warned about was live and was avoided.** Sequence step 4
was done before step 7. Confirmation that it mattered: the two gates now produce
**134 prerendered `builders/*` HTML files and 176 `sectors/*`** in the after
build, and every per-tenant count is unchanged. Had the projection not been
widened, `templateKeyFor(tenant)` would have returned `undefined`, both gates
would have returned `[]`, and the build would still have reported success.

**Cache keys: none changed, and none needed to.** `lookupClientBySlug`'s
`unstable_cache` key parts are `["client-by-slug"]` plus the `slug` argument.
Next's own `unstable_cache` documentation
(`node_modules/next/dist/docs/01-app/03-api-reference/04-functions/unstable_cache.md`)
states it "already uses the arguments and the stringified version of your
function as the cache key", so the slug — the only thing that varies the result —
is already in the key. Nothing else in this increment is cached.

**`revalidatePath` / `revalidateTag`: none added.** No Server Action in this
increment writes anything, so there is no mutation to revalidate. No cache tag
was added to `lookupClientBySlug` — CD-03 owns that.

**The 300s window is documented, not fixed.** Every AC 6 / AC 7 evidence step
stopped the dev server, `rm -rf .next`, ran the SQL, then restarted — making the
result deterministic instead of racing the window. That is why the observed

### Defect 1 — `templateKeyFor` was not actually fail-closed

`lib/templates/index.ts`. `key in TEMPLATE_REGISTRY` walks the prototype chain,
so `constructor`, `toString`, `valueOf` and `__proto__` passed the registry
check and were returned as a `TemplateKey`.

```ts
return Object.hasOwn(TEMPLATE_REGISTRY, key) ? (key as TemplateKey) : undefined;
```

The finding was correct, and the framing was the important part: my own comment
on that function promised that an unrecognised value "returns `undefined`
exactly as a null does". The code did not make that true, so the comment
overstated a guarantee — the defect class this repo cares most about. The fix
makes the existing comment true, so no comment rewrite was needed; I added four
lines explaining *why* `hasOwn` rather than `in`, so the next reader cannot
"simplify" it back.

This mattered concretely, not just theoretically. Before the fix,
`template_key = 'constructor'` produced
`TEMPLATE_REGISTRY["constructor"].urlSlug` → `undefined` → every internal link
became `/realestate/undefined/<slug>`, and `data-template="constructor"` matched
no palette. CD-03 is about to put this column behind a dashboard form.

### Defect 2 — `scripts/seed-client.ts` wrote `profile.template` unvalidated
